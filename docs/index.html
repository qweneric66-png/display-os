                01业务起点

                先定义业务终态，再设计技术流程

                发现的问题

                如果把代码跑通、接口返回或文件生成当作完成，项目仍可能无法回答“用户能不能真正使用”。

                我的判断

                完成标准必须落在业务结果上：用户看得懂、能判断、能继续操作，而不是只证明技术动作执行过。

                落地动作

                先写终态验收句，再拆输入、处理、输出和异常；项目分析、展示和交付都围绕这句话组织。

                结果证据

                当前多个项目已能独立展示名称、封面、能力说明和边界；真实业务终态仍按项目继续补充验证。

                方法沉淀先定义“什么算成功”，再决定要做哪些功能。

                可复用场景网页采集、RAG、商品发布、工程建模。

                02事实基础

                把不可靠输入转化为可核验事实

                发现的问题

                网页、截图、OCR、表格和模型输出可能互相冲突；单一来源看似完整，也可能把推断伪装成事实。

                我的判断

                必须保留来源，区分事实、推断、候选和假设，并把冲突与缺失显式留给后续判断。

                落地动作

                为业务对象建立稳定身份和关系；SolidWorks 尺寸进一步区分明确、推导、视觉估计、临时假设与待确认项。

                结果证据

                商品、SKU、项目资产和工程参数已按对象身份组织；证据不足的内容保留边界，不直接升级为确定结论。

                方法沉淀先确认“什么是事实”，再让 AI 或规则基于事实工作。

                可复用场景网页采集、OCR、商品资料、RAG、CAD 参数确认。

                03责任边界

                把 AI 放在适合它的判断位置

                发现的问题

                AI 很容易把相似项目写成同一套能力；候选内容未经判断就执行，会让结论比真实证据走得更快。

                我的判断

                平台提供事实，AI 理解和生成候选，规则检查资格，人工确认风险，专业工具执行，验收层回查终态。

                落地动作

                用项目身份、证据状态和页面门禁约束候选；低置信度、参数冲突和发布动作保留人工确认。

                结果证据

                PDD、Reddit、LEX 和跨境调度项目已呈现不同能力组合；未验证内容不会被包装成确定结论。

                方法沉淀不问“AI 能不能全做”，而问“谁有资格做这一步判断”。

                可复用场景项目分析、内容生成、商品发布、工程参数确认。

                04可恢复流程

                让长任务有状态、可暂停、可恢复

                发现的问题

                生成、保存、切换和重启后内容不一致时，“页面上有结果”不等于任务可继续，更不等于业务完成。

                我的判断

                任务必须按业务对象隔离状态；成功结果要保留，异常要定位到对象和阶段，浏览器状态不能成为唯一事实来源。

                落地动作

                设计创建、运行、暂停、恢复、失败和回查状态，使用检查点、幂等和人工门禁支持局部重试。

                结果证据

                已用多个项目验证切换与重启后的资产隔离；旧项目结果不会覆盖当前项目，缺失内容才进入待生成。

                方法沉淀长流程同时设计状态、检查点、异常接管和重新验证。

                可复用场景批量采集、AI 审核、内容生成、文件交付。

                05失败与评测

                用反例和分层证据证明结果

                发现的问题

                页面能打开、测试通过或样本很多，只能证明局部成立；一个真实反例仍可能否决阶段成功。

                我的判断

                代码实现、测试通过、现场运行和业务终态必须分开表达，结论强度不能超过最强有效证据。

                落地动作

                依次执行离线只读、在线影子、灰度门禁、业务回查和失败样本复测，并把未验证项单独标出。

                结果证据

                当前 UI 已完成桌面与窄屏检查；真实项目质量、长期稳定性和业务指标仍按证据边界表达。

                方法沉淀失败样本会改变规则、评测集和验收条件，而不是只被修掉。

                可复用场景AI 输出、数据平台、工程产物、运营工作台。

                06经验复用

                把失败经验沉淀为规则和资产

                发现的问题

                同类偏差会在项目分析、UI 交付、RAG 和工程建模中重复出现，单次修复无法阻止下一次漂移。

                我的判断

                真正可复用的是问题边界、处理步骤、失败样本、证据要求和验收标准，而不是一句漂亮提示词。

                落地动作

                把反例转成回归测试，把稳定判断整理为 Skill、UI 规则、交付门禁和项目成长档案。

                结果证据

                多个本地 Skill 和跨项目 UI 门禁已经可被调用、检查和持续修订；新经验仍需通过真实项目验证后再升级。

                方法沉淀真实问题 → 根因 → 验证 → 规则 → 回归 → 跨项目复用。

                可复用场景项目分析、质量治理、协作交付、个人能力成长。

                07可追溯交付

                用归档和版本化保持结论可复查

                发现的问题

                需求、方案和修复如果只存在于聊天记录里，下一次遇到同类问题就只能重新猜，也无法判断历史结论是否仍有效。

                我的判断

                重要变更必须回答为什么改、改了什么、如何验证、风险在哪里；历史证据不能直接冒充当前事实。

                落地动作

                保留前置备份、版本目录、根因、修改范围、验证结果和风险，让交付事实可以被复查和恢复。

                结果证据

                当前迭代已形成前置备份、任务归档和成长文档联动，页面判断可以对应回具体版本事实。

                方法沉淀把“我记得怎么做”升级为“团队可以按证据复现”。

                可复用场景Bug 修复、架构升级、UI 改版、交付复盘。

                08协作边界

                用双机协作划分共享资产与本机状态

                发现的问题

                本机路径、账号、缓存和运行状态不能直接搬到另一台电脑；只同步文件却不重新验证，也会制造“看起来能用”的假象。

                我的判断

                协作要共享可复用资产，隔离机器差异；同步完成不等于交付完成，恢复后仍要检查入口、依赖和真实环境。

                落地动作

                区分源代码、配置模板、Skill、文档、测试与凭证、路径、缓存、日志；分享页面时保留可展示内容，运行能力单独确认。

                结果证据

                当前项目已区分本地服务和分享展示边界；跨设备运行仍以目标环境复核为准，不把本机状态包装成通用能力。

                方法沉淀同步可复用资产，隔离机器状态，恢复后重新验证。

                可复用场景GitHub 分享、双机开发、现场交付、团队协作。
