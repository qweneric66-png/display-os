                01终态反推法

                系统显示成功，可能正是最大的业务风险

                先定义业务真正完成的证据，再反推状态、异常、补偿和页面。

                主案例跨境 ERP 商品发布机制已落地
                反直觉判断问题不在接口稳定性，而在系统把“成功”定义错了。
                背景与问题

                文件生成或接口受理后，商品仍可能因类目、图片、价格或审核失败而不可售。技术完成掩盖了业务失败。

                问题重构

                技术执行、平台受理和业务成功是不同事实，不能压缩成一个 success 状态。

                关键取舍

                只增加重试会重复提交，也无法解释商品停在哪一段；因此先拆成功定义，再设计补偿流程。

                结果与证据

                系统可区分未提交、未受理、审核失败、已上线但不可售，并将异常定位到具体商品和阶段。

                架构变化
                V1文件生成 / 接口返回→ success
                V2提交 → 受理 → 审核 → 上线→ 在线可售
                沉淀方法终态反推法

                以用户可确认的最终事实为起点，而不是以现有接口为起点。

                验证边界

                状态与回查机制已有项目证据；在线可售率提升尚无完整对照数据。

                可复用

                订单履约、财务到账、内容发布、工程建模、RAG回答和数据同步。

                02否决记忆法

                系统不只要记住选中了谁，还要记住为什么没选

                把人工否决从操作噪声变成负样本，让候选空间持续收敛。

                主案例跨境选品 Agent流程已有运行记录
                反直觉判断选品系统稀缺的不是召回更多候选，而是减少同类错误候选再次出现。
                背景与问题

                Amazon发现、Takealot竞品验证和1688寻源跨平台运行；人工删掉的不合格候选，下次任务仍会重复出现。

                问题重构

                系统只保存正样本，没有保存价格、结构、评论或信息完整性等否决原因，人工判断无法积累。

                关键取舍

                没有把关键词、结构、价格、评分和图片混成黑盒总分，而是逐层收窄，图片只做最后辅助复核。

                结果与证据

                候选池、人工复核、否决原因与搜索游标形成连续流程，支持从已检查位置补充候选和阶段续跑。

                架构变化
                旧流程重新搜索 → 重复候选→ 再次人工删除
                新流程候选 → 规则 → 人工否决→ 记忆原因并续查
                沉淀方法否决记忆法

                把拒绝原因作为下一轮召回、过滤和评测的输入。

                验证边界

                续查与阶段产物有运行证据；候选有效率提升仍需统一人工标注后计算。

                可复用

                招聘筛选、供应商评估、内容审核、销售线索和设计方案选择。

                03证据资格门禁

                证据不足时，系统应该拒绝给出完整结论

                先判断数据有没有资格回答问题，再决定是否允许进入分析。

                主案例Amazon 评论洞察真实反例驱动
                反直觉判断最大风险不是少采几条，而是把残缺证据包装成完整洞察。
                背景与问题

                Amazon部分场景只展示有限评论，采集程序可以正常结束，但样本并不代表完整用户反馈。

                问题重构

                “程序已完成”“页面数据已保存”“数据足以分析”“结论可用于判断”是四种不同状态。

                关键取舍

                继续分析会让流程更自动，却制造虚假确定性；因此宁愿暂停，也不让无资格证据进入正式结论。

                结果与证据

                系统识别登录、验证码、限流与部分展示；不完整时保存现场、标记边界并禁止正式分析。

                门禁流程
                证据完整采集 → 完整性判断→ 允许分析
                证据不足保存现场 → 标记缺口→ 暂停 / 转人工
                沉淀方法证据资格门禁

                正确回答之前，先验证输入是否足以支撑这个回答。

                验证边界

                门禁、警告和禁止分析已有实现记录；评论覆盖率受平台可见范围限制。

                可复用

                RAG、OCR、财务审核、市场研究、法律检索和工程图纸解析。

                04双契约编译架构

                不要让模型直接操作专业软件，先把意图编译成可审查规格

                把不确定的语义理解与确定性的SolidWorks执行解耦。

                主案例AI 辅助工程设计工作台架构已形成
                反直觉判断建模失败不一定是模型不准，更可能是语义判断与工具执行耦合后无法定位责任。
                背景与问题

                草图、图片和语言存在尺寸缺失与关系歧义；直接生成API命令，错误通常到建模后才暴露。

                问题重构

                需要分别回答“要设计什么”和“SolidWorks执行什么”，两类错误应当独立校验。

                关键取舍

                没有追求一步到位，而是在两份契约之间加入尺寸、材料、关系、缺失项检查与人工确认。

                项目价值

                失败可定位为输入不全、规格冲突、执行命令或现场环境问题，任务可以修改规格后重复执行。

                双契约编译
                语义契约草图 / 图片 / 语言→ 可审查工程规格
                执行契约规则校验 / 人工确认→ SolidWorks建模任务
                沉淀方法双契约编译架构

                AI先编译领域规格，再由确定性执行器编译成专业工具操作。

                验证边界

                规格与执行任务结构已有项目实现；复杂装配的端到端成功率仍需样本评测。

                可复用

                CAD、财务记账、数据库修改、商品发布、自动采购和工业控制。

                05异常产品化

                异常不是一段错误文本，而是一个等待被推进的业务对象

                围绕影响、责任和恢复路径组织异常，而不是围绕错误码组织页面。

                主案例跨境 ERP 异常中心53 / 90 条已处理
                反直觉判断异常中心的目标不是证明系统报过错，而是帮助业务恢复。
                背景与问题

                错误码和接口日志无法告诉运营哪些商品受影响、是否严重、能否重试以及谁来处理。

                问题重构

                异常需要拥有受影响对象、发生阶段、业务影响、处理资格、责任人与下一步动作。

                关键取舍

                技术详情保留在证据层，主界面只展示业务结论、严重程度和可以执行的恢复动作。

                结果与证据

                一次真实处理中完成53/90条修复，当前待办由90条收敛至37条。

                异常对象模型
                输入受影响商品 + 失败阶段→ 判断影响与资格
                输出责任人 + 修复动作→ 从失败阶段恢复
                沉淀方法异常产品化

                让异常具有对象、状态、责任、处置资格和恢复路径。

                验证边界

                53/90是单次真实处理证据，不代表长期自动修复率或整体稳定性。

                可复用

                审批流、批量采集、数据治理、内容审核、任务调度和供应链系统。

                06权限随证据升级

                不要问AI总体好不好，要问它在这一步能拥有多大权限

                同样的准确率，用于搜索关键词和修改库存，风险完全不同。

                主案例ERP × 选品 × RAG × 工程设计评测框架已形成
                反直觉判断AI自动化程度不应一次决定，而应随着证据和可恢复能力逐级开放。
                背景与问题

                单一准确率不能说明一次错误会造成什么损失，也不能决定模型结果是否有资格自动写入业务系统。

                问题重构

                评测对象从“模型整体表现”改为“当前步骤的风险、权限、验证方式和失败恢复能力”。

                关键取舍

                价格、库存、类目、金额和工程尺寸等高风险字段，不因平均表现较好就直接自动执行。

                落地方式

                按离线只读、在线影子、人工确认、受限自动和业务回查五个阶段逐步提升权限。

                离线只读→在线影子→人工确认→受限自动→业务回查
                沉淀方法权限随证据升级

                自动化权限由风险、证据、失败样本和回滚能力共同决定。

                验证边界

                分阶段机制已形成；接受率、修改率、拒绝原因和回滚率需要继续积累。

                可复用

                所有会写入真实业务、财务、平台或专业工具的AI能力。

                07反证优先洞察

                用户洞察不是找一句支持想法的话，而是主动寻找能推翻它的反例

                把RAG从答案生成器升级为主张、支持证据与反对证据的争议系统。

                主案例Reddit 用户洞察与 RAG方法待补评测
                反直觉判断高频声音不等于普遍需求；经得住反证的主张才有资格进入产品决策。
                背景与问题

                普通RAG容易把若干相似帖子总结为“用户共识”，忽略反对意见、情境差异和特定人群。

                问题重构

                用户洞察应回答谁在什么场景遇到问题、证据是否冲突，以及当前材料能支持多强的结论。

                关键取舍

                模型只生成候选主张；出现反例时，结论必须降级为特定场景假设或待验证机会。

                目标输出

                每个主张同时保留支持证据、反对证据、适用人群、使用场景、证据强度和待验证问题。

                洞察单元
                主张支持证据 + 反对证据→ 判断证据强度
                边界人群 + 场景 + 冲突→ 产品假设 / 待验证
                沉淀方法反证优先洞察法

                先寻找能够推翻主张的材料，再决定结论能否升级。

                验证边界

                当前适合作为方法设计表达；反例样本、人工一致率和洞察采用率仍需补齐。

                可复用

                市场研究、需求优先级、舆情、竞品分析、战略研究与知识问答。

                08经验编译系统

                聊天记录不是组织能力，能被下一次直接执行的规则才是

                把一次问题解决过程编译成事实档案、成长判断、Skill规则和验收门禁。

                主案例跨项目 AI 协作基础设施已持续复用
                反直觉判断保存更多对话不能避免重复犯错，必须把判断变成可执行约束。
                背景与问题

                AI辅助开发会出现上下文丢失、不同电脑结果不一致、版本覆盖和修改原因无法追溯。

                问题重构

                聊天是过程数据；真正可复用的是问题边界、取舍依据、失败条件、执行步骤和验收标准。

                关键取舍

                没有把所有历史塞给AI，而是分离当前事实、个人判断、通用规则和项目级验证证据。

                结果与证据

                归档、成长档案、Skill与UI交付门禁形成分层机制，已在多个项目中持续调用和修订。

                经验编译
                项目事实改了什么 / 为什么改→ 成长判断
                可复用资产Skill规则 / 失败边界→ 验收门禁
                沉淀方法经验编译系统
